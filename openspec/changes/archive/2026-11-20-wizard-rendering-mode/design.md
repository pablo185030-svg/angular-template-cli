## Context

The public template is SSR: `angular.json` has `server: src/main.server.ts`, `outputMode: "server"` and `ssr.entry: src/server.ts`; `app.routes.server.ts` sets `RenderMode.Server`; `src/server.ts` is an Express app; `app.config.server.ts` and `main.server.ts` bootstrap the server; `package.json` has `@angular/ssr`, `express` (and types) and `serve:ssr`; the `Dockerfile` runs `server.mjs`; `nginx.conf` proxies to Node. `scripts/configure-theme.mjs` and the CLI's `generate.js` already show the pattern: a script inside the template, run by the CLI as a reported step, with its logic exported for tests that import it from the template.

## Goals / Non-Goals

**Goals:** one question and flag; a template script that converts SSR to SSG or SPA; template stays SSR and simple.
**Non-Goals:** shipping three templates, converting back to SSR, hybrid per-route modes (editing `app.routes.server.ts` covers that), changing the backoffice.

## Decisions

- **Script is one-way from SSR.** It detects the SSR state (`outputMode: "server"` in `angular.json`) and errors otherwise. Going back is `git checkout`/regeneration; embedding the SSR files in the script would duplicate them. The summary says so.
- **SSG:** `angular.json`: `outputMode: "static"`, remove `ssr` (the Express entry); keep `server: src/main.server.ts` (prerendering needs it). `app.routes.server.ts`: `RenderMode.Prerender`. Remove `src/server.ts`, `serve:ssr`, `express` and `@types/express`; keep `@angular/ssr`. Output is `dist/<name>/browser`.
- **SPA:** remove `server`, `outputMode`, `ssr` from `angular.json`; delete `main.server.ts`, `server.ts`, `app.config.server.ts`, `app.routes.server.ts`; remove `@angular/ssr`, `express`, `@types/express`, `serve:ssr`; drop `provideClientHydration` from `app.config.ts` if present. The `environment.ssr.allowedHosts` block is left in place (harmless, documented) to keep the script small; revisit if lint flags it.
- **Container and nginx:** both static modes replace `Dockerfile` with an `nginx:alpine` image copying `dist/<name>/browser` into the html root, and `nginx.conf` with a static server block (gzip, `/health`, long cache for hashed assets). SSG uses `try_files $uri $uri/index.html =404`; SPA uses `try_files $uri /index.html`. Templates for these files live as strings in the script.
- **Dependencies:** the script edits `package.json` only; `package-lock.json` is left stale and regenerated by the next `npm install` (the wizard's own install step, or the user's). The script says so in its output.
- **Placeholder name:** the script reads the project name from `package.json`, since generation already replaced `coto-angular-template`.
- **Logic exported** (`applyRendering(projectDir, mode)`) so tests run it on a copy of the template, like `configure-theme`; CLI integration tests inject `runNode`.
- **CLI:** `--rendering` parsed with `parseArgs`, validated, rejected for backoffice. Prompt is a `select` after the dark mode question with Spanish hints (SSR: "Mejor SEO, necesita un servidor Node"; SSG: "Páginas prearmadas, hosting estático simple"; SPA: "Solo cliente, sin SEO"). Generation step "Configurando el modo de renderizado" runs after the dark mode step when mode is not SSR. Non-interactive default: SSR.
- **Verification:** `scripts/verify-templates.mjs` already builds each template; add a verify variant that converts a copy to SSG and to SPA and builds it, so the conversions cannot rot.

## Risks / Trade-offs

- Prerender output layout for the static build must be confirmed during implementation by actually building; the nginx `try_files` rules follow from it.
- Stale lockfile until the next install: documented, and the plain `npm ci` would fail, so the summary keeps `npm install` as the next step (consistent with the install question change).
- Converting is destructive on the generated project only (never on this repository's template).
